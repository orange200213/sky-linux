English summary of the session handoff (`handoff-20261106.zh.md` is the original). Scope of the
session: **fill the 4 GB of RAM, fix USB gadget DMA, and stabilise touch.**

The touch driver is **built-in** (`CONFIG_TOUCHSCREEN_NT36XXX_ML=y`); the touch firmware is
loaded at run time from `/lib/firmware/novatek/nt36672c.bin` (FW_VER `0x18`). Networking and
SSH come from the `initramfs-m2` initramfs, which mounts UFS and switches to `/mnt/skyroot`.

## 2. 4 GB memory fix

The DT used to describe a single 1.6 GiB segment, so Linux only ever saw ~1.1 GB. The memory
node now lists the five segments of a 4 GB unit:

```dts
memory@80000000 {
	device_type = "memory";
	reg = <0x0 0x80000000 0x0 0x68e00000>,
	      <0x0 0xf1300000 0x0 0x0ed00000>,
	      <0x8 0x00000000 0x0 0x3fe00000>,
	      <0x8 0x40000000 0x0 0x3c700000>,
	      <0x8 0x7cd00000 0x0 0x01e00000>;
};
```

Measured: `free -m` → **Mem: total 3259 MB**.

## 3. USB gadget fix (needed *because* of the memory fix)

With high memory enabled, the gadget started failing with
`dwc3-qcom a600000.usb: unknown endpoint event 0` — the controller was doing DMA above the
32-bit boundary without an IOMMU mapping. The USB node now declares the SMMU stream ID the
vendor DT uses:

```dts
iommus = <&apps_smmu 0x540 0x0>;
dma-coherent;
```

Never change the high memory segments without re-validating DWC3, or that fault comes back.

## 4. Touch: what changed in this session

| change | detail |
|---|---|
| **reset GPIO dropped** | the driver no longer requests `reset-gpios` (GPIO12); this board resets the controller with its **SPI soft-reset** command, exactly like the vendor driver which also leaves GPIO12 unclaimed. `ts->reset_gpio = NULL`. |
| **first-frame wait fixed** | new `nt36xxx_report_is_live()`: `0x77` is this firmware's *valid idle* frame, `0xfd`/`0xfe` (and uniform `0xff`) are reset states. The old code treated any non-`fd/fe` read as usable, so a half-initialised IC was published as "downloaded". |
| **wait is bounded and fatal** | up to 100 × 5 ms (≈500 ms) for a live frame; on timeout the download is **not** marked complete (`goto release_fw_buf`), so the normal panel-cycle retry still happens instead of an IRQ storm. |
| **reset-state check is fatal** | if the IC does not reach `ReK`, log `sky: IC failed to reach ReK` and abort the download instead of continuing with a half-initialised controller. |
| **panel 1.8 V rail** | `vreg_panel_1p8` (gpio97, from the stock `qcom,oled-vdd1v8-gpio`) is now `regulator-always-on`, so the panel/touch supply does not drop between init attempts. |

Expected boot sequence:

```
sky-fw: part 0 ILM ... / part 1 DLM ...
sky-repair: ... bad=0
sky-crc: flag=0x04
sky-fwinfo: fw_ver=0x18
sky-report[0]: 777777777777 state=a3...      ← 0xa3 = NORMAL_RUN, 0x77 = idle
```

One runtime recovery was observed and healed itself in ≈1.3 s (`sky-recover[1]: reports all
0xFD/0xFE` → new download → `fw_ver=0x18` → `state=a3…`), with `errors=0 timedout=0` in the
SPI statistics: this is the IC entering its own reset state, not an SPI transport failure. If
it starts happening frequently, investigate touch supply, ESD/watchdog, display power
transitions and SPI timing.

## 5. Do not do

1. Do not turn the touch driver into a module — the current boot flow depends on it being
   built-in.
2. Do not restore the single 1.6 GiB memory segment (it silently caps RAM at ~1.1 GB).
3. Do not touch the high memory segments without re-validating DWC3 DMA/IOMMU.
4. Check `current-slot` before flashing `boot_a`/`boot_b`.
5. The first firmware download should happen once; a single FD/FE recovery at run time is
   currently accepted, repeated ones are not.
6. `sky-shim-boot-v4.img` is the build script's generic output — always copy it to a
   feature-suffixed name for a deliverable, so nothing gets overwritten.
